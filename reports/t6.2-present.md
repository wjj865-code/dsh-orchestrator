## 2. `task_status` 产物区块（T6.2 本体）

### 2.1 实际渲染

`task_report` 回报了 3 条产物（1 个普通文件 + 1 个目录 + 1 个不存在的路径）后：

```text
任务「带产物（1a2b3c4d）」
状态：已完成
子会话：s-1
目标：g
产物：共 3 条（可交付 1 条）
- C:\Users\...\report.md — 报告
另有 2 条产物不能交付（目录 1、不存在 1）
交付：在你自己的回合里调用 present，files 里每项 path 填上面这些绝对路径（1-2 个最关键的，最多 4 个）；插件已 stat 校验存在且是普通文件，不要另找路径。
最近消息：
- [brief] ...
```

无产物时（同一个工具、另一个任务）：**没有**任何 `产物：` 行——与通知的「无可交付候选就不写指令」保持同一取向，不写一句会诱发失败 `present` 的话。

### 2.2 口径与通知的一致性

| 口径 | 通知（`artifactBlock`） | `task_status`（`artifactLines`） | 是否一致 |
|---|---|---|---|
| 可交付判据 | `classifyPath`：绝对路径 + `lstat` 是普通文件 | 同一个函数 | ✅ 同一份代码 |
| 候选上限 | 4（`PRESENT_MAX_FILES`） | 4 | ✅ |
| 折叠文案 | `另有 N 条产物未列出` | 同 | ✅ |
| 跳过统计 | `另有 N 条产物不能交付（目录 x、不存在 y…）` | 同 | ✅ |
| 交付指令 | `PRESENT_HINT` 原句 | 同 | ✅ |
| 首行 | `产物：` | `产物：共 N 条（可交付 M 条）` | 仅此处不同（`counts: true`）：验收要求「条数正确」，状态查询需要能一眼看到总数 |
| 无产物 | 不渲染 | 不渲染 | ✅ |

> 为什么 `task_status` 只列「可交付」而不把目录路径也打出来：混进清单就是给模型一个会被 `present` 整次拒绝的路径（平台先 `lstat` 判 `entry.type !== 'file'` 就报错）。目录/链接以计数形式出现，既解释了「为什么少了」，又不诱导交付失败。

### 2.3 与「面板是产物库」的分工（沿用 T6.1 结论）

- 面板（`client.js`）继续显示台账全量产物（含目录、`（未找到）`），定位是**产物库**，不是交付候选 → 本单不改面板。
- `task_status` 是**交付候选清单**（喂给 `present` 的那一份），所以只列普通文件。
- 想全量看路径：`task_detail`（子会话）与面板。

## 3. D5 偏差修复（结算通知带 artifacts）

### 3.1 修之前的两处缺陷（T6.1 报告 §5）

| # | 缺陷 | 原证据 |
|---|---|---|
| 1 | 结算通知 payload **没有** `artifacts` 字段 | `src/settlement.js:64-79` 的 `notifier.push({...})` 里没有 artifacts |
| 2 | 产物补齐发生在通知**之后** | `index.js`：先 `settlement.report(input)`（内部已 `notify`），再 `collectAfterSettle(outcome)` 才 `setTaskArtifacts` |

结果：「子会话自然结束 → 结算自动判 done」这条**最常见**收场路径，通知里永远没有产物，也就没有 present 交付指令。

### 3.2 修法

1. **payload 带产物**（`src/settlement.js:74-84`）：`artifacts: Array.isArray(task.artifacts) ? task.artifacts : []`。字段恒定存在（空数组也是值），渲染层据此决定要不要写产物区块；`test/settlement.test.js` 对 payload 只做单字段断言，加字段安全。
2. **新增 `beforeNotify` 钩子**（`src/settlement.js:58-61`、`:162-171`）：

```text
transition → 落 settle 消息 → beforeNotify(task, status) → notify(补齐后的行) → 释放可写根 → goal 收口 → pump
```

   钩子返回 `undefined/null` 表示不改；返回对象则用它的产物渲染通知；`outcome.task` 也改成钩子后的行（调用方不必再查库）。
3. **`index.js` 改接钩子**：`collectAfterSettle(outcome)` 改写成 `collectArtifactsBeforeSettleNotify(task, status)`（`index.js:332-357`），逻辑不变（`collectWorkspaceArtifacts` + `appendMissingArtifacts` + `setTaskArtifacts`），但**返回**补齐后的台账行；`reportSettle`（`:403-406`）只剩 `settlement?.report(input)`，「通知后收集」那段整体删除。
4. **顺序不变量有测试兜住**：`test/settlement.test.js:123` 断言钩子收到的是「刚进终态、产物 0 条」的行、而 `pushed[0].artifacts` 是钩子补进去的那条路径——把顺序倒回旧实现，这条用例立刻红。`test/index.test.js:866` 再从 `apply()` 层面验证同一件事（注入给协调者的文案里真有 `- <path> — +3/-0`）。

### 3.3 失败语义

| 场景 | 行为 |
|---|---|
| 钩子抛错 | 记 `task.settle.before-notify-failed`；终态保持；通知照发（产物退化为台账现值） |
| 会话已释放 / 服务缺失 | 钩子返回原任务；通知里是台账里已有的产物（可能为空） |
| 非 `done` 终态 | 钩子直接返回原任务（收集只对 `done` 生效，与原来一致） |
| 结算重复到达 | 状态机天然幂等（`not-running` 直接跳过），不会重复收集/通知 |
